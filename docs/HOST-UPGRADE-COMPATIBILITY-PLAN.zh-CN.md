# Codex App 升级兼容性修改方案

日期：2026-09-14。代码基线：`main` / `16c439dd0bf3657ba06707ff15c1465613d49554`。

状态：原生全局安装、准确 Hook 信任、旧入口退役和本任务实际 Hook/MCP、独立委派验收已完成；其它旧任务的自动接入服务已部署，自有原生连接中断后的自动恢复也已现场验证。旧任务需在再次使用、出现准确新入口且当前工作到达安全空闲边界后接入，不能将服务部署完成表述为全部历史任务已迁入。本轮未重新执行 Windows 登录态验收或实际 App 二进制升级实验。开发证据见[开发验收记录](evidence/host-upgrade-compatibility-20260914.zh-CN.md)，最终安装及接入状态见[全局安装记录](evidence/host-upgrade-global-install-20260915.zh-CN.md)。

## 1. 用户目标与交付标准

Codex App 正常升级后，只要插件实际使用的 Hook、MCP、子代理、消息和执行结果契约仍兼容，插件应继续完整工作。App 版本号、发行通道、可执行文件重新构建或安装位置变化，不应单独造成委派失效、资格被撤销、遗留消息卡住或反复要求人工操作。

本方案以插件侧实现为前提，不要求修改 Codex App 或新增宿主接口。插件更新隔离与宿主升级兼容是两个问题：前者继续保护任务使用的业务实现，后者负责让该实现正确理解新宿主发来的实际事件。

交付必须同时满足：

- 正常升级后，已有任务、新任务、休眠后恢复的任务均能继续委派、补充要求、读取结果和结算。
- 同一任务在升级前启动的子代理、命令、消息和未结责任不会被丢弃、重派或重复结算。
- 单纯 App 版本或程序摘要变化，不创建新的资格子代理，不进入故障恢复流程，也不让用户反复重新信任未改变的 Hook。
- 真正的接口不兼容只影响依赖它的功能；明确区分不兼容、缺少证据、暂时不可读和信任被撤销。
- 不以“以后由主任务执行”作为兼容问题已修好的验收结果。

用户主动停用插件、撤销 Hook 信任、删除依赖文件或实际调用来源不可验证，仍按各自真实原因处理；这些不应被统称为 App 升级不兼容。

## 3. 把兼容性落在真实依赖上

新增宿主兼容模块，内部集中管理已审查的证据契约和验证器。契约按功能命名，例如 `hook-dispatch/1`、`child-lifecycle/1`、`message-delivery/1`、`native-operation/1`、`spawn-capacity-rejection/1`；不再命名为 `codex-某版本支持表`。

同一验证器可以覆盖多个 Codex 版本。新版本号本身既不是拒绝条件，也不是放行证明；收到的实际内容必须满足该验证器要求。

分离以下对象：

| 对象 | 内容 | 用途 |
| --- | --- | --- |
| `hostObservation` | 观测到的版本、平台、路径、程序摘要、观测时间和来源；允许部分信息缺失 | 诊断、排查和原始证据追溯，不单独授予或撤销业务能力 |
| `dependencyContract` | 实际使用的 Hook 事件、执行方式、参数语义、返回语义、父子身份、消息和终态规则、适配器摘要 | 判断某一功能是否兼容 |
| `taskQualification` | 本任务的真实 Hook 派发、信任状态、插件实现身份、作用域，以及已经建立的契约证据 | 防止借用另一个任务或临时进程的资格 |
| `operationEvidence` | 原始 call/turn/author/child、输入、输出、原始字节摘要、实际使用的契约和验证结果 | 结算特定操作、检测冲突；创建后不改写 |

插件自身代码、票据、真实执行来源和 Hook 信任仍受完整性校验。不能借本次改造忽略插件文件篡改、任意缓存目录重定向或新的执行命令。

展示文案等不参与业务语义的字段从功能摘要分离。Hook 的 `command`、`matcher`、`async`、执行来源、启用和信任状态必须检查；timeout 的变化需判断是否仍满足所需执行时限。宿主原始 Hook 信任 hash 不由插件重算或替代。

对输入格式实行明确的扩展规则：契约已定义为描述性信息的区域允许附加字段；工具动作、执行状态、输入消费、身份和终态等区域必须可解释。未知动作不能当成无工作事件忽略。单纯新增描述信息不应自动造成整条生命周期失效。

## 4. 兼容模块的接口与实现位置

对调用者只暴露两个主要操作，具体读取、格式识别和历史适配放在模块内部：

```text
inspectHostCompatibility(context, requiredCapabilities, currentEvidence)
  -> compatible | checking | incompatible | trust_required
     + evidence references + affected capability + concrete reason

verifyHostOperation(operationReference, rawEvidence)
  -> verified operation proof | unresolved responsibility
```

`verified operation proof` 必须由验证器根据真实来源生成，绑定输入、结果和证据快照；不能接受调用者填入 `passed=true` 或自行声明没有未完成操作。只读检查不消费票据、不回收预留、不制造 outcome。

建议新增 `host-compatibility.mjs` 和内部 `host-contracts/`；复用现有 rollout reader、身份解析和操作账本，避免再建一套并行的“任务完成”状态机。

业务运行时仍保存版本和阶段归属。宿主契约选择按**具体操作及证据段**记录：旧父任务创建于 A、升级后在 B 发出 followup，不能用父任务的创建版本解释 B 的调用；一份长日志也不必属于同一种宿主实现。

稳定入口、MCP 和 Hook 必须调用同一兼容模块。不能只改 MCP 准入而让旧 Hook、恢复 CLI 或结果 reader 继续按旧版本表拒绝。

## 5. 正常升级后的自动流程

### 5.1 无感路径是默认路径

在 `SessionStart/resume` 或下一次真实 Hook/工具操作时记录宿主观测变化。若本任务当前可信来源、所需 Hook、输入输出投影和依赖契约仍成立：

1. 追加观测记录，保留原任务资格和历史 proof。
2. 继续原阶段及正常委派，不创建新的资格子代理。
3. 每条后续操作按实际结果正常验证；旧调用仍核对其原始证据。

仅版本、App 安装位置、磁盘二进制摘要、发行通道变化，不进入 `failed`，也不触发 qualification refresh 或恢复票据。读取版本失败同样不能否定已经充分证明的实际能力。

“契约仍成立”至少要求当前真实任务的可信 Hook 记录和所需接口证据，没有冲突或反证；不能仅凭文件存在、RPC 握手成功或没有报错作结论。

### 5.2 只有实际证据不足时补证

优先读取当前任务 Hook、实际工具回执和可验证的历史记录。只有所需契约尚未建立、发生真实相关接口变化或一次性证明格式迁移需要时，才补做有界检查。

- 使用现有原生工具；不得要求用户选择模型、复制状态或人工跑测试。
- 首次生命周期补证可使用现有无业务子代理，正确记录 Pre/Start/Post/Stop、原始源和唯一 outcome。
- 无业务子代理只证明对应生命周期能力，不能证明消息拒绝、命令结束、取消、恢复和回收的全部语义。
- 补证沿用正常容量和责任账本。不得为探针挤掉业务、突破名额或绕过未消费票据。容量不足时保留明确的待补证状态，后续真实事件再推进。
- 必须解决启动循环：补证派发前只要求可信父任务 Pre、票据、目标 model/effort 和载体校验，不预先要求尚未产生的 child 身份或完整资格。实际 Start 后建立父子关系，Post、Stop 后分别验证派发结果和完成事实；缺失任何一步都保留对应责任。全过程不获得业务工具权限，也不以版本白名单作为前置条件。

已有功能的有效证明不因无关能力正在补证而失效。未建立某项必要证据时，不虚构该能力可用；记录具体缺项，而不是显示“整个插件不支持当前 App”。

### 5.3 不重复检测、不形成新锁

正常命中使用当前 Hook 证据和有界缓存，不每次重新读取整个程序、扫描所有任务日志或启动临时 app-server。契约验证实现和无状态解析缓存可以共用；任务资格和真实操作证据不能跨任务共用。

补证按实际来源、能力和作用域合并并发请求。等待项必须有持有者、原因、下一触发条件和可核验的操作引用。超时、暂时读不到文件或进程退出不会转为永久“不支持”，也不能自动转为成功。

新消息、Hook 恢复、原始记录可读或所需能力发生变化时，按既有责任继续检查。已经有真实副作用的调用不能因重试计时到期而重发。

数据库写事务只做短的证据快照/状态比较与提交；原始日志扫描和外部调用在事务外完成，共享截止时间。提交前重核文件身份、输入 revision、当前契约和状态；并发变化使本次提交失效，不覆盖新结果。

## 6. 按功能处理能力变化

| 功能 | 必须验证 | 不应因为何种变化失效 |
| --- | --- | --- |
| 新委派 | 当前任务真实 Hook、信任、完整载体、指定 model/effort、原生父子关联、所需终态证据契约 | 仅 App/CLI 版本或二进制摘要变化 |
| 补充任务和消息 | 同一原生 call 的输入、实际接收/拒绝结果；接收与被子代理消费分别记账 | 旧 child 由其他版本创建；新调用来自升级后宿主 |
| 最终结果和 outcome | 当前 revision、全部要求处置、最新 final/完成事件、Stop、无未结操作 | 原宿主程序已被更新；当前宿主与旧调用观测不同 |
| 命令/进程/cell | 每个真实句柄及其代际、原生开始/结束、对应 Hook/FileChange/调用结果 | 外层工具名称或非语义元信息变化 |
| 启动前拒绝/容量拒绝 | 特定操作的完整原始调用与结果、准确拒绝语义、无子活动证据、票据状态及二次快照 | 不在旧版本表中 |
| 对账、归档读取、维护 | 原始归属、完整记录、仍有效的证明、所有剩余责任 | 当前新委派能力暂时不可用 |

拒绝恢复尤其不能把“相同错误字符串”当成通用未派发证明。只有该契约能证明拒绝发生在派发前，才能按失败收尾并释放对应预留。泛化错误、超时、重复结果、迟到 child 或覆盖不完整继续保留责任。

允许通过完整原生结果补齐丢失的 Post 记录所代表的事实，不补造 Hook 事件。发送成功只代表接受请求；消息尚未被 child 消费时不能结束阶段。主任务可以正常继续不受影响的工作，但不能用此行为代替尚未恢复的插件能力。

## 7. 宿主来源与重启恢复

临时启动的 app-server、PATH 中的 CLI、正在运行的 Desktop 任务和子代理必须分别标明来源。临时 app-server 的 `initialize`、`hooks/list`、`model/list` 或 `thread/read` 成功，只证明该端返回了相应数据；不得代替真实任务当前回合的 Hook 派发和子代理事实。

macOS 从进程路径读到的磁盘文件可能已经被更新，不能用它宣称旧进程正运行该新版本。Windows 不能依赖 macOS 祖先进程方案；使用已有原生调用、Hook 和父子证据建立能力。无法读取诊断版本时，如果这些证据仍齐全，正常功能继续。

重启只改变执行环境，不改变业务责任。分别覆盖 Pre 后、Start 后、Post 前、Stop 后/outcome 前、命令运行中和消息待消费的重启：先读取现有 attempt/message/operation，再决定等待、对账或继续同一阶段。不得把旧会话创建版本当成当前 followup 的执行版本，也不得自动重派原业务。

缺少证据只阻断需要它的操作；历史读取和对账路径不能被“当前新委派尚未可用”挡住。只要实际关键契约未变，应能通过已有原生证据自动恢复；需要用户动作的场景限于宿主确实要求重新信任、权限被撤销等真实边界。

## 8. 数据结构与历史证据

采用加法迁移，新增契约定义/引用、任务契约资格、宿主观测和逐操作契约关联；尽量复用现有加密 journal 与 operation ledger。新记录有明确 schema；契约定义保存验证器代码摘要，不能由 JSON 文件自报兼容获得权限。

- 旧 schema、旧 receipt、旧 outcome 和原始证据逐字保留，旧 reader 继续可读。
- 新调用采用新 schema，不回填、重签或修改旧调用的 `hostEvidenceDigest`。
- 一个版本可以匹配多个功能契约，一个功能契约可以适用于多个版本。
- 不以 App 版本创建一套 Hook 或插件包。相同契约升级只增加有界观测记录。
- 尚被阶段、操作、消息、回滚和宿主入口引用的契约/包不能删除；观测裁剪不删除未结责任的原始证据。

旧 qualification schema 只保存综合摘要，没有完整可分离的 host/hookSet 原像。不能通过“去掉版本字段重新算 hash”把旧记录改为 passed。迁移优先重读仍可取得的原始 route/outcome/Hook/源记录，结合当前真实 Hook 建立新契约依据；资料充分时不创建子代理。只有确有缺项时才进行证明格式迁移所需的有界补证，保留旧结果原文，不能把首次迁移统一实现成每任务一次探针。

## 9. 首次接入旧任务：必须另做兼容交接

当前稳定壳静态导入自己的 dispatch/lifecycle，所选运行时还会导入自己的旧资格模块。当前升级规则同时冻结 writer/shell 摘要，且要求所有责任清空。**所以本次实现不能直接使用现有普通热发布，也不能仅发布一个新适配器就宣称旧任务已生效。**

### 9.1 先区分真实入口

| 旧任务实际使用的入口 | 可采用的路径 | 必须证明的边界 |
| --- | --- | --- |
| v2 稳定壳、动态选择 service 的旧 MCP | 新增插件内部 compatibility epoch，保留原壳字节，由 registry 选择新运行时 | 旧壳→新 Hook、旧 MCP→新 service、旧 lifecycle wrapper→新 qualification 三条实际调用均成立 |
| v1 直接执行旧 Hook，或不能参与运行登记的冻结入口 | 宿主现有原生恢复/入口重载后，验证该任务及 child 已进入可派发壳 | 不能把安装完成、`hooks/list` 更新或发生重启当作该任务已切换的证据 |

v2 路径要求候选包保留旧调用方能解释的 descriptor、entrypoint、tool 和 storage 形状。旧 MCP 的 `settleCandidate` 仍调用旧 `settleRuntimeMigration` 和旧资格 reader，**新 epoch 必须自行核验和提交接入，不能向旧 candidate 流程塞入新 schema 证明，或伪造旧资格 passed。**

v1 旧 writer 不会自动执行新代际检查，也不会读取新增的接续表。只有真实原生入口退役/重载证据才能解除这一限制；若现有宿主能力做不到，必须把具体旧任务列为未接入阻塞项，保留其包和责任。不得称所有任务已受保护，也不得通过改写旧目录绕过限制。该可行性在 P0 确认，不能留到上线后发现。

### 9.2 v2 接入与责任接续协议

1. **准备和双向互操作。** 在独立数据区准备不可变候选包，验证真实已安装基线与候选共读写账本。旧 `RouterStore` 构造会执行 schema setup 和历史对账，测试必须包含这些旧 reader/writer；新证明使用旧 reader 不会误解释、清理或覆盖的加法记录。准备阶段不改变现有任务和阶段的执行绑定。
2. **任务绑定和历史阶段同时处理。** 空闲任务核验来源和历史资料后建立新契约资格。旧 child、消息 target、carrier 及 `record_outcome/manage_stage` 会优先定位原阶段，不能只更新 task/default。首次被 Router 观察也不等于新任务：从未调用 Router 的休眠旧任务要依据原生出生证据和原入口识别。
3. **区分原始归属和后续执行方。** 为已停止 child 的待消费消息、待核验结果或延期责任增加显式接续。不可变 origin 保留原 root/context、route、child、ticket/dispatch、runtime generation、原始 proof/outcome。追加唯一 epoch receipt，绑定前后执行 generation、源摘要、输入/消息 revision、未决责任、验证器和状态比较基准。为兼容旧 dispatcher，若更新 `runtime_stages.generation`，必须明确定义其为有效执行方，先保存原值及完整接续链；不能把新运行时追溯记成旧阶段创建者。
4. **已核验的操作静止点。** 普通升级期间在途阶段 writer 固定；此次显式接续只改变静止点后的执行方。正在运行的 child turn、命令/cell、未完成 Hook/MCP 调用、未消费启动票据和消息投递结果 unknown 必须先等待/对账。UI idle、进程消失和 TTL 到期都不足以证明静止。已经确认投递、child 停止且尚未消费的业务输入可以原样保留，不要求取消需求或先把业务做完。主任务原生 code-mode 终态只证明其解释器已返回；其中未核验的业务效果以加密原责任保留，不解释为业务完成。原生进程终态须同时对应准确任务、轮次、句柄、命令或原生轮询，复用句柄、缺失回执和当前在途调用继续阻断。此主任务迁移投影不得用于 child 收尾或预留回收。
5. **原子交接。** 新 epoch verifier 在事务外核对原始源，进入短的 `BEGIN IMMEDIATE` 后重核 task/stage/invocation/消息 revision、来源快照和接入依据，原子追加 receipt 并切换有效执行方。必须证明所有可能参与的 v2 入口在同一事务规则下登记调用；任何不能参与的旧 writer 都先按 9.1 处理。并发调用已进入则本次切换取消并保留旧方，不能假设旧程序会执行新增检查。交接中断由唯一 receipt 对账恢复。
6. **继续原责任。** 不新建业务 route、不重发 ticket、不重复投递已 accepted 的消息，也不复制 outcome。原调用和迟到回执按它们的原始身份与证据契约核验；没有新增契约记录的旧调用由历史 reader 重读原始源。新解释另记依据，不补造历史 Pre/Start/Post/Stop。child followup 未必再次触发 Start，因此要核验它后续真实工具/Stop 已经进入新运行时，并保留旧 coverage 起点。
7. **确认真实生效。** 当前真实 Hook 和一次正常所需的只读 Router 调用须证实旧壳实际选择了新运行时。确认前状态为“待接入验证”，不开放依赖尚未建立证明的新操作；不因这个确认单独创建子代理。候选失败时保留旧包、原始结果和责任；回退也必须经静止点及接续记录验证，不能重置账本。

已结算的历史 child 没有正在交接的执行，不要求为其另开一轮来制造新 Hook 记录。例外必须同时满足：原 outcome 存在、child 已 settled、维护不 active、最新原生输入/操作/final/Stop 全量复核 ready，且当前闭合 token 与原 verified revision/digest 或已核验维护 token 完全一致。缺项、迟到输入、源变化和陈旧 token 均不适用。receipt 记录 `verified_settled_history`；它不写入 child 入口确认，未来真正 followup 仍须经过新执行方的真实 Hook。

已经信任且不可变的稳定壳可以保留。新版协调器只接受经代码审查的准确已部署入口源码契约，验证其真实登记和原 Hook 调用，并由该原入口自己的不可变退役验证器复核原退役/恢复链；不重写旧证明的验证器指纹。准确旧壳到新引擎还必须有源码管理的实际互操作 publication。准备和提交均核验入口字节与登记，候选只进入受管引擎区，不新增原生 Hook 缓存或信任。

显式整任务接入的日志扫描在写事务外共享 15 秒预算，不消耗随后 5 秒的准备令牌有效期。冷消息检查点在提交前使用自己的既有有界读取；完成后才开始独立的 5 秒提交预算。提交前后均检查真实来源身份，准备过期、提交超时和来源变化分别报告，任何失败都不切换绑定或遗留半份收据。普通 Hook、阶段收尾和预留回收的预算保持原值。该划分避免长历史记录挤占事务窗口，也不允许无限持有写锁。

本机隔离原生实验已证明父任务及原 child 可以在新进程中恢复并运行 B Hook，且 child followup 不再触发 SubagentStart；实验同时发现，原生 `send_message` 的 accepted 回执不能证明尚未消费的队列已跨进程保存。因此冷交接还必须具备未消费要求的加密检查点及显式接续记录：保留原 sender call、输入、回执和来源，不把新输入冒充成原输入；只有真实新补充已到达同一 child、最新结果与操作均已复核，根任务才能核验原要求的处置。未经检查点保全或来源存在冲突时保留具体责任，不能仅凭新 final 跳过原消息。后续原消息迟到同样必须重新核对，不能静默忽略。

这套跨 writer 接续机制是新增开发内容，现有 `beginRuntimeMigration` 不能直接承担。开发首先验证入口可达性、双向数据兼容和接续原子性；没有证明之前，不安装、不放开普通 writer 检查，也不把“仅新任务正常”当作验收完成。

首次安装仍遵守用户此前“不影响正在运行任务”的要求：开发和候选验证在独立目录/数据区进行。若真实原生安装会删除旧缓存或旧壳必须重新加载，只在明确安全的安装窗口切换；无需依赖自动重开程序，安装与用户手动重开可以分开。未来普通 App 升级不因此重复安装插件或创建新的 Hook 目录。

### 9.3 接入 epoch 后的普通发布

共享默认 A 仍供未接入任务和冻结入口使用。已接入 B 的任务若发布同 writer/shell 的 C，需要在该契约下记录普通默认和真实 B/C 互操作证明，不直接把全局默认从 A 改成 C。每个不同的历史 writer 仍须与已审查 epoch 端点有字节核验过的兼容依据；不能只检查 schema 或图上可达。

原 epoch receipt 的 B 不改写成 C。C 的实际 Hook/调用必须属于当前 task、stage 或合法 candidate，并与该 epoch 基线的 writer/shell 契约一致。候选阶段继续使用原有资格和收尾限制，B 的已确认入口不能替 C 放行业务。成功后保留 B 的原始证明和阶段来源；失败按原候选流程恢复 B。历史已结束 stage 仍可能运行 B，不能因为 root 已在 C 就拒绝其正常 followup 或维护。原生边界的 CAS 必须同时覆盖契约内普通默认的变化。

### 9.4 一次性冷安装的具体入口

`runtime-admin.mjs` 分别提供 `prepare-cold-epoch`、`install-cold-epoch`、`retire-cold-epoch` 和 `restore-cold-epoch`。这些是新增的明确操作，不放宽原 `coldLegacy` 冻结 Hook 的检查，也不修改旧目录内的代码。

| 步骤 | 实际动作与结果 |
| --- | --- |
| 准备 | 读取准确 A/B 包，执行旧、新 writer 互操作验证；将被原生安装器删除的旧包保留到受管目录，同时迁移登记的读取地址。task/stage 执行归属保持原值 |
| 保全要求 | 对已接受却未消费的消息保留加密 checkpoint，绑定原 sender call、原输入、真实返回、child 静止点和源快照；unknown 调用或运行中操作先完成核验 |
| 原生安装 | 验证冷进程边界后调用现有 `plugin/install`，以实际 exit 确认自有安装进程已退出；不自动写入 Hook 信任 |
| 旧入口退役 | 检查原路径，原生安装后仍存在的已登记绝对壳路径单独归档；只有准确旧入口全部不可执行且进程静止，才追加退役收据 |
| 每任务接入 | 原父任务的真实 B 入口到达后，按静止点、原责任及 CAS 交接；仍需执行的 child 核验其实际入口，已完全核验结算的历史 child 适用第 9.2 节保留例外。安装成功和目录变化不能代替任务接入证据 |
| 恢复旧入口 | 冷窗口中恢复保留的原始字节，先追加恢复事件使旧退役收据失效；已有 B task/交接记录时必须先核验回退，不能直接覆盖 |

`installationComplete:false` 表示只完成安装或退役子步骤，不能解释为所有任务已接入。重复执行退役或中断后继续，通过原始路径、保留包和不可变事件链对账，不重写业务 outcome。以后仅 App 版本变化时不执行这一套插件冷安装。

### 9.5 未消费消息的保全与接续

新源码的 `runtime-epoch.mjs checkpoint-inputs` 可在冻结旧工具库存之外，使用明确的 context、route、revision 和原父任务日志引用建立检查点。接入 B 后，`manage_stage` 的 `read_checkpoints` 读取责任，`resolve_checkpoint` 核验它的处置，`resolve_checkpoint_arrival` 审核随后真实到达的原输入；冻结的原生工具 schema 使用已安装新版的单次 stdio bridge，不要求新开任务。

此消息恢复能力同样适用于已运行新版插件的普通任务；日常 App 重启不一定存在首次插件交接的 epoch 记录，因此该记录不能成为消息责任恢复的必要条件。准入与消息处置分别验证，不用一次消息恢复给任务授予尚未取得的新委派资格。

原始宿主密文只作不透明的身份比对与加密保留，不解密、不作为文本重新发送。主任务从原上下文恢复可读要求，向同一个 child 发出明确补充。新收据必须绑定这次实际 followup、新消费输入的 ID 和密文、最新 final/Stop、所有操作终态以及主任务对原要求的审核。原 accepted 记录保留，不能将其改成“原消息已消费”或“发送被拒绝”。

原消息迟到或证据变化必须单独处理：没有真实消费和新结果时继续保留责任；已经被同一 child 实际消费并完成时，允许主任务按原输入与最新结果追加明确处置，保留之前的接续收据。阶段已经结算后发生的迟到也应重新出现在当前责任检查中，保持原 outcome 不变。不能丢弃迟到消息，也不能把这个可核验状态永久锁住。读取、解析在写事务外共享截止时间，事务内只做来源身份、revision 和状态比较后提交。

### 9.6 旧任务接入的自动推进

本机实际验证暴露的部署缺口是：单任务协调器成功退出后，其它旧绑定不会因正常 Hook 自动完成 epoch 交接。旧绑定总数包含未使用和历史记录，不能据此批量迁移或唤醒全部任务。补全为仓库根 `scripts/` 下的独立调度器及针对性测试，运行副本单独受管；它从固定 C2 不可变包调用既有准备、提交和入口确认 API，不修改插件包、稳定 B Hook、原信任或全局默认。

调度器只处理原生发现的非归档旧根任务，排除用户明确暂不处理的任务 `01a08905-50bf-7051-9f76-29c3d7fc811a` 及永久废弃的 Windows Codex 项目。名单在发现、定向读取和提交前均执行。原生 `id/cwd` 用于查询真实 Router 绑定；没有实际已完成的 B 根入口时仅保留等待状态，不读整份历史。新 B 任务和已接入 C2 任务不纳入旧任务迁移。

已实测当前 CLI 支持 `thread/list` 的 `archived:false`、`sortKey:updated_at`、降序、根来源筛选和 `useStateDbOnly:true`。每轮最多两页，低频查询近期页并接续真实游标；持久化更新时间边界及同秒 ID，重叠去重，不以严格大于时间戳跳过同秒变化。不支持当前可选参数时降级为低频有界原生分页，不能改为全盘 JSONL 扫描。日志身份、原生更新时间和完成入口仅触发重新尝试，不证明空闲；正在执行的任务在独立 app-server 上也可能呈现 `notLoaded`，其最新 turn 元数据还可能呈现 `interrupted`。

每次只对一个有新证据的候选调用原 C2 的资格继承、`prepareHostEpochHandover` 与紧随其后的 `commitHostEpochHandover`。真正活动的根/child、unknown 执行和投递、来源或责任归属不明确继续阻断；确定停止且能够原样保全的业务要求和未知业务效果按原 C2 契约接续，不清理或伪称完成。第一次重新进入旧任务的活动轮不能承诺立即迁入；留下真实入口并结束后才交接，之后由该任务自己的真实 Hook 和正常 Router 读取确认，无需重开 App 或新建任务。

独立的 0600 原子状态保存配置边界、发现进度、每任务证据指纹、原因、退避及收据；它仅用于调度，不是准入凭证。同证据的真实责任阻断等待来源变化，暂时 RPC 故障到退避期满可重试；新实际入口或相关来源变化清除旧指数退避，但保留最低冷却时间。准备 token 不持久化。提交后状态写入前崩溃时从原 runtime/epoch/receipt 恢复，不重复提交或回滚。固定 launchd 服务与进程退出自动释放的操作系统锁保证单实例，不能依据锁文件年龄抢占；退出只关闭自有客户端，不控制 App 或其他任务。App 替换原生程序或自有客户端退出后，由服务有界重启、重新读取真实宿主边界与轻量游标；不能永久持有失效连接，也不能因宿主标签变化否定业务资格。

准备中的 `verifying` 状态不代表已经得出拒绝结论。服务在读取元数据或准备 token 后退出，下一进程应先对账真实收据，再在冷却期后重新准备；不能把未完成尝试永久当成同证据阻断。临时证据不可用必须贯穿初次 Hook 读取、历史资格的前后复检和最终交接准备；保留原验证器的具体原因，不把超时统一改成缺少可信绑定。实际信任、身份、Hook 集合和未决责任拒绝继续等待来源变化。

验收覆盖排除项、归档与无入口任务不产生历史读取、同秒分页及游标失效、证据驱动重试、跨进程互斥、崩溃恢复和原证明拒绝路径。部署运行、真实任务接入和真实入口确认分开报告；没有合格旧任务时不能制造一个用于宣称实际迁入成功。

## 10. 开发拆分和交付顺序

| 步骤 | 主要修改 | 结束条件 |
| --- | --- | --- |
| P0 固定行为与迁移可行性 | 梳理所有版本判断；建立隔离的旧壳/旧 writer/休眠任务 fixture；验证第 9 节接续路径 | 关键入口可达性和状态交接均有可运行反例；不存在必须改宿主的前置条件 |
| P1 契约模块 | `host-compatibility`、`host-contracts`、`native-lifecycle-audit`、`native-recovery-audit` | 同契约的新版本被接受；同版本的关键协议变化被识别 |
| P2 资格与自动检查 | `native-host-executable`、`hook-readiness`、`lifecycle-qualification`、`runtime-lifecycle`、`app-server` | 元信息变化不重发资格；真实证据来源不混用；补证可进入且能收尾 |
| P3 逐操作收尾与恢复 | `stage-reconciliation`、各 recovery/audit 模块、`native-operation-evidence`、`stage-closure` | 消息、失败拒绝、执行句柄和历史收据在升级前后连续正确 |
| P4 数据与旧任务接续 | schema reader、registry/dispatch、兼容 epoch、接续 receipt、精确旧入口桥接及安装验证 | 旧任务、休眠任务、延期阶段、新旧 reader/writer 混跑和回滚全部通过 |
| P5 体验与验收 | Hook/Skill 提示、诊断字段、三平台 CI、macOS 和 Windows 原生登录态验收 | 完整矩阵通过，真实任务无新增卡锁或反复自检；才能安排全局安装 |

P0–P5 属于同一个功能交付，不能只上线 P1 就宣布问题解决。诊断只在状态有实质变化时提示；正常升级匹配不刷屏。提示必须区分具体缺失能力、暂时等待和真实不兼容，保留可核验的原因。

## 11. 验收矩阵

| 场景 | 必须达到的结果 |
| --- | --- |
| 仅版本号变化，包括 alpha 到 stable、未出现过的标签 | 同一实际契约下完整功能继续；不新建资格子代理 |
| 同版本重新构建、程序摘要变化或 App 安装路径变化 | 仅观测记录变化；原任务资格、原收据和未结责任不变 |
| 运行旧进程时磁盘程序已被替换 | 不将磁盘新版本误记为旧调用的执行证明 |
| 版本读取失败但当前可信 Hook/原生操作完整 | 不因诊断信息缺失停用功能 |
| 增加契约允许的描述性字段 | 正常解析；不撤销全部资格 |
| 同版本缺少必要 Hook、关键字段/动作语义变化 | 识别具体受影响能力，不靠版本相同放行 |
| Hook disabled/trust 撤销、matcher 漏匹配、执行来源改变 | 真实边界仍生效；不自动重写 trust |
| 临时 app-server 正常，真实任务当前 turn 没有 Hook | 不能借临时进程证明委派可用 |
| 旧 parent＋新 child；旧 child＋新宿主 followup | 保留原父子和阶段，按新调用实际契约处理 |
| 成功 send/followup 尚未消费；升级后才消费 | 消费前不能收尾，消费后能正常结算 |
| 新宿主产生完整、可证明的启动前或容量拒绝 | 按实际失败收尾；不留永久预留，不伪造成功 |
| generic error、重复 ticket/result、迟到 child 或只有错误文案 | 保留对应未决责任，不能推断无 child |
| 新调用换宿主，旧拒绝收据未变 | 旧收据继续有效；新增调用独立验证 |
| 篡改同一旧调用的 host observation/input/result | 原有防篡改反例继续失败，不能借兼容性绕过 |
| final 之后仍有命令/cell、句柄复用或缺最新 Stop | 不误结算，不误回收 |
| 在 Pre/Start/Post/Stop/outcome 各窗口重启 | 原 attempt、消息、阶段和唯一 outcome 连续一致 |
| 日志被归档、追加、截断、替换或转向另一路径 | 合法归档可恢复；变化/不完整证据按真实原因保留责任 |
| 多任务并发遇到同一次 App 升级 | 不出现全局自检风暴；任务证据不互借，数据库不被扫描长期占锁 |
| 原生名额或全局预留满额时需要补证 | 正常回收规则继续有效；不突破限制、不借机丢掉消息或业务 |
| 旧 schema 资格缺原像 | 原文保留；从真实资料建立迁移证明或补证，不填造 passed |
| 休眠旧任务恢复且带待处理消息/延期责任，包括此前从未调用 Router 的旧任务 | 正确识别原入口和阶段，按显式接续协议继续；不要求新开任务、取消需求 |
| 新旧 writer 并发、交接中断、候选失败及回滚 | 无双写/双重消费，旧结果不被覆盖，未结责任完整 |
| v2 冻结 MCP、旧 Hook 路径、旧数据库初始化和 candidate reader | 三条真实加载路径成立，旧代码不误处理新证明；新 epoch 不借旧 candidate 结算 |
| v1 直接 Hook 及不能参与运行登记的入口 | 真实原生接入及旧入口退役得到验证；做不到则明确阻塞，不宣称全量完成 |
| 连续多次 App 升级仍使用同一契约 | 不增加 Hook 注册和插件版本目录；资格探针次数不随版本数增长 |
| macOS 与 Windows 原生登录态链路 | 各自真实执行委派→补充→完成→结算，不能以另一平台或 CI 替代 |

验证分三层：确定性的契约/异常反例测试；隔离进程与新旧包互操作测试；真实 macOS/Windows 登录态验收。合成修改版本字段只能证明判断逻辑，不等于真实 App 升级验收。实际升级验收要记录升级前后宿主与插件的真实来源、任务/child/消息引用及结算结果。

## 12. 本次方案核验与依据

方案阶段完成源码、回归用例和只读函数核对，复现版本、程序摘要和路径摘要对资格的影响。独立审查覆盖资格准入、消息收尾、拒绝恢复、真实宿主来源及旧运行时注入点；修订后的设计已通过该阶段复核。后续开发、反例、完整测试的失败项及原生验收边界持续记录在[开发验收记录](evidence/host-upgrade-compatibility-20260914.zh-CN.md)，方案阶段的认可不代表实现已经验收。

主要官方依据：

- [Hooks](https://learn.chatgpt.com/docs/hooks)：Hook 来源、事件、输入输出和信任由宿主提供；新/变更的 Hook 需要按实际定义审查。插件不能自行继承变更后的 trust。
- [ChatGPT & Codex changelog](https://learn.chatgpt.com/docs/changelog)：协议模型、通知和 Hook 元数据确实会演进。示例变化不能当作本机特定 App 构建已兼容或不兼容的证明。

本方案不承诺识别所有未来未公开的语义变化。它要求取消人为版本封锁，利用实际契约和逐操作证据保持兼容，并在发现真实差异时精确处理；不能用未知标签推断失效，也不能用外观相似推断操作已经安全完成。
