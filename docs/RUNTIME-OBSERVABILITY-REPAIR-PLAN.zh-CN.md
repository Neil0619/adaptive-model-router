# 运行观测整改与验收

本次整改来自真实运行审查：部分请求拒绝与异常没有可关联记录，日志保留范围不明确，旧资格和冷升级恢复缺少可靠的失败边界。本文件记录最终行为、验证边界和遗留限制；原始运行日志、宿主配置与任务身份保留在本地证据目录，不随源码发布。

## 已交付的行为

- Router 请求及 Hook、launcher、stdio bridge 记录脱敏关联事件，区分收到、结束、成功、拒绝、降级和失败；调用结束不代表业务成功。
- 记录真正进入的 runtime、shell 和阶段所属版本；声明身份、历史未知来源与可信原生身份分别呈现。
- 观测记录有时间、全局容量和单任务容量界限，独立记录裁剪及丢失覆盖；没有记录不能解释为没有发生。
- 巡检通过私有只读数据库快照分页、按时间范围检索，不创建或迁移原数据库。旧 schema、损坏观测库和缺表均明确报告。
- outcome 可关联有界验收摘要；附件不代替原生生命周期、当前 closure token 或根任务核验，原 outcome 的身份和历史不改写。
- MCP 名称或参数校验失败时，只有唯一匹配的可信原生 Pre 才能结清为 rejected；歧义、异任务和未知来源保持未结。校验拒绝不进入业务 store、不迁移 schema、不新增业务路由。
- 仅在外部 JSON 请求边界把语法错误标为 `INVALID_INPUT`；合法请求遇到内部持久化 JSON 损坏时返回脱敏的 `INTERNAL_ERROR` 并记录失败，不再归咎于调用者。stdio bridge 保留明确的输入错误码，MCP 帧解析仍使用协议错误 `-32700`。历史校验恢复继续固定旧依赖原字节，不接受新版依赖冒充旧校验行为。
- 已证明的两类历史资格问题使用独立恢复收据；缺原件、晚到输入、身份冲突或检查期间变化均保留阻断。恢复本身不授予新的业务委派资格。
- 重复冷升级的登记、publication 和可恢复 installation 原子提交；失败恢复准确前像，不复活已退休入口或丢弃历史责任。
- 复制安装包的测试 candidate 在重新计算摘要前移除继承的安装绑定；真实安装包及启动器绑定保护不作修改。

该 CI 修复后的源码包摘要为 `512149dad7964b284368704b15a88ea2e68f2ea186756ac1df7bc193d0ad6dcc`，writer digest 不变。对应验证见 [CI 修复验证摘要](evidence/runtime-observability-repair-20260922-ci.json)；该文件与首轮快照分别保留，远端最新检查以相应提交的 CI 记录为准。

第二轮 CI 的 Linux、macOS 和 Windows Node 24.15 检查通过，Windows Node 24.x 暴露 stdio 测试的两处问题：测试总时限包含进程启动，却仅给输入超时检查 2 秒；另一测试在进程树未收尾时删除 SQLite 夹具，报 `EBUSY` 并可能覆盖原始失败。后续修复只调整测试：分离 20 秒宿主总时限与产品计时、等待 `close`、处理 stdin 错误、有界终止自有进程树，并在失败时保留夹具与完整诊断。无法核实 Windows 异常退出后的后代清理时明确保留，不宣称清理成功。产品输入时限和 15 秒 MCP 时限未修改。独立真实进程探针及反例分别核验延迟启动、延迟收尾、缺少 EOF、无输入、无响应、提前退出和终止失败；这些探针不代表已知原 CI 锁持有者。

stdio 测试修复后的源码包摘要为 `7fa5b397040ec03798bc38d375fcbeee00d09a5b2fe9c36ca9e9f65965713342`，writer digest 仍不变。验证与保留的失败证据见 [stdio 测试修复摘要](evidence/runtime-observability-repair-20260922-stdio.json)。

源码提交、CI、已安装包与实际宿主验收是独立事实；Git 提交不更改已信任 Hook 或当前任务运行时。未来产品代码更新仍须冻结新包、核验对应信任并通过用户可见安装流程。

## 验收边界

| 范围 | 状态与判据 |
| --- | --- |
| 源码回归 | 隔离测试、结构/契约校验、双语离线路由评测；具体计数及跳过原因见公开验证摘要 |
| 已安装包 | 本机实际安装回执、七个精确 Hook 信任、原生注册、安装源/缓存摘要及默认运行时一致；不包含最后新增的错误分类修复 |
| 已安装包的 macOS 真实运行 | 已观察到新入口、资格与普通委派、宿主模型意图保护及 finally 恢复，MCP 开始/终态和关联账本交叉核验通过 |
| 已安装包的当前长期任务 | 正式 handover 后真实 Hook/MCP 及新普通子任务进入已安装包，唯一 outcome 收尾，原任务与历史结果保持身份 |
| 新增错误分类修复 | 源码回归与独立私有夹具实际进程验证通过；尚未重新打包安装，不能沿用已安装包的登录态验收作为这次修复的发布验收 |
| Hook 覆盖 | 两段真实 macOS 窗口合计观察到七种 Hook；不宣称每段窗口都覆盖七种 |
| Windows 原生运行 | 本轮缺可用宿主，未测；跨平台 CI 不能替代登录态宿主验收 |

宿主模型切换仅用于有明确所有权的临时测试目标，由原生宿主接口执行并恢复。路由器不改变主任务模型；根任务推理档位仍由宿主管理。

## 保留的历史限制

- 一个旧 smoke 在票据产生后没有对应派发、随后被标记歧义。完整归档与保存前缀相符，但不存在受支持的权威无子任务终态证明；原占槽未释放，没有补造普通 outcome 或复用票据。
- 一个历史任务的原日志前缀没有匹配原件；当前全量记录不能反向证明旧前缀完整，不重新锚定。
- 13 条早期路由没有新观测事件；上线后的覆盖不能补齐这段历史。
- legacy 原始历史与当前资格合同不兼容的失败保留，不改写为成功。
- 一份旧验收辅助预检原文件曾被工作文件覆盖，原摘要和原生命令结果保留，完整原字节不可恢复。后续附件按摘要独立留存，不用重跑替代原始证据。

以上限制分别记录为未恢复、证据不足或未测，不以源码通过或本机安装成功统称完整历史整改完成。缺少新证据时不自动重复恢复，也不要求用户反复查找未知备份。

## 运维与后续责任

安装和升级必须显示阶段、用时、实际宿主阻塞及最终结果；退出 Codex 前暂停相关自动跟进。源码整理本身不启动冷安装。新增产品修复由维护者接续冻结新包、验证升级兼容性与精确 Hook 信任，再提供可见安装入口并完成实际运行验收；本次源码提交和审查不能替代这些步骤。

历史资格恢复入口及拒绝条件见 [历史资格验证恢复](HISTORICAL-QUALIFICATION-RECOVERY.zh-CN.md)；观测 schema、保留范围、巡检和附件约束见 [运行观测说明](RUNTIME-OBSERVABILITY.zh-CN.md)。历史占槽恢复需要受支持的可信宿主证据，Windows 登录态验收需要可用原生宿主；这些条件具备后再执行对应验收。
