## 为什么任务归档后仍是 39

原生 Codex 的任务归档只改变任务状态和 rollout 所在位置。已安装 Router 没有把这个变化连接到版本目录退休。cache 是全局共享的版本包，vault 是这些版本的全局恢复副本，两者都不是每个任务单独一份；任务数与版本数没有一一对应关系。

上次操作把 61 个 vault 中的 22 个未索引孤立版本移到了外部归档；39 个 cache 和 39 个已索引 vault 当时仍在原目录。本次检测确认：用户后来归档任务，没有进一步归档这些版本。上次的 22 个版本归档仍然是历史事实，不能把它表述成所有已归档任务的版本都已处理。

安装器会恢复索引内的历史 cache。只移 cache 会重新长回来；移 cache 和 vault 而保留索引项，会在后续安装或修复时触发 `RUNTIME_VAULT_DAMAGED`。本次协调处理 cache、vault 和同一版本的索引项，保留活动指针及其失败版本黑名单字符串。

## 全部使用新版后，能否归档全部旧版本

可以把真正没有运行依赖的旧包全部移到外部归档，但“新版已设为默认”只决定新绑定，不证明旧任务已经离开旧版。退役判断应针对版本的实际引用：

1. 当前默认版保留；明确选中的回退版保留。放弃该回退目标必须是单独明确的决定，不能在清理中顺手修改。
2. 未归档任务的旧入口、当前完整资格、正在运行的进程或子代理，以及未完成、延期、未知操作需要的版本继续保留。
3. 已归档任务只有在没有这些执行或责任引用时，才允许把它独占的旧版 cache/vault 和对应索引项一起外移；共享版本要等最后一个引用释放。
4. 先保存可以核验的原路径恢复材料，再退休引用与搬移文件；搬移失败能恢复一致状态。归档包可供以后恢复，永久删除是另一项操作。
5. 取消归档或再次复用旧子代理时，先按清单恢复它实际需要的原路径并验证，再恢复执行。索引、资格、恢复材料与任务状态应共同校验，不能只把 archived 改回 false。

已归档、无责任任务的历史包因此可以外移；已完成迁移、没有旧入口或旧阶段责任的新运行体系也不需要无限保留所有发行版。保留多少由这些引用和回退策略决定，不由总任务数或固定 39 个决定。

## 当前自动化边界与恢复

本次是完成一次实际检测和受控归档。现行 v1 和待安装的 v2 **都尚未实现原生任务归档/取消归档到入口退休/恢复的自动联动**。v2 已有包引用检查和允许归档的历史阶段包恢复，但 `runtime_tasks` 和 `runtime_host_entries` 仍有长期引用；不能把它表述为本问题已经自动解决。

未来自动化需要在任务边界或维护扫描中读取可信原生归档状态，分开处理业务责任、任务绑定、宿主入口和可恢复包。未知项保留且显示原因；只有引用真正消失后才退休。上线前还应覆盖共享版本、已归档但延期的子代理、取消归档先恢复、搬移中断、并发归档状态改变等反例。
